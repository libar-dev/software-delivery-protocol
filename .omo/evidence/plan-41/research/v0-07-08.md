## Scope and method

Chapter 07 sections 1–3, 11 and 12 are already captured as `pack:spec-studio-v1` (12 Specs, all
`scoped`, 27 keyed open questions). This map covers the rest of chapter 07 (§4 interaction patterns,
§5 projections, §6 patch loop, §7 harnesses, §8–10 lenses in detail, §13 AI integrations, §14 the loop)
and all of chapter 08. Where a Studio Pack member already holds a claim, the row names it.

Each claim was checked with at least two concept searches in different words (`g.findByConcept`), a
grep of `specs/` and `docs/concept/`, and `g.byFile` on the code that might realize it.

Status values:

- **realized**: a Spec states it and the engine realizes it.
- **captured-ahead**: a Spec states it below `ready` or without implementation. "Question only" means
  the claim is held whole by a keyed open question and nothing else.
- **departed**: a ruling refuses it. Most rows cite a `ready` decision Spec. Rows marked
  **(no decision record)** rest on a non-decision Spec or a concept-doc principle instead. That
  difference matters for the owner's direction (see "Departures worth re-opening").
- **uncaptured**: no Spec states it and no ruling refuses it. "Concept-only" means a surviving concept
  doc names it as aspirational but no Spec does.
- **out-of-scope**: v0 itself deferred it, or it is runtime plumbing with no bearing on the Protocol.

Relevance is to the owner's goal: designs held ahead of code, iteration from several perspectives,
review, design-versus-realization tracking, decisions and open questions, AI-native graph reading.

## Departures worth re-opening

1. **The patch loop, as an addressed proposal and not as a codemod.** The edit model keeps views from
   writing source. Concept 06 §4 lets a structured edit contract return only when a second machine
   writer appears. The adopter now has two:
   - advisor agents, whose memos propose "exact text for a Spec, with the entry address it replaces
     or follows" (`task-pass.md`);
   - writer agents, which apply the rulings, while `decisions.py apply <patch>` applies JSON patches to
     the register.

   What looks better now is v0's envelope (§6.2) without its apply machinery: a proposal that names
   its base commit, its rationale and its proposer, keyed by entry address and checked by address
   resolution (recipe 25) before an agent applies it. The conformance and honesty checks stay the
   gate, with no speculative apply and no ts-morph codemod. First give the departure a decision
   record. Today it has none.
2. **HTML first for human review.** Concept 06 §5 settles generated Markdown for the MVP, and
   `#primarySurface` is still open. The adopter's one Pack page is 2,725 lines of Markdown with folded
   lists. Feedback 02 asks for a table of contents, reference previews, entry links, search and
   keyboard navigation. This is v0 §1's "Markdown caps out" argument, measured on the first adopter.
   Agents stay the first sink. The human view would move from Markdown pages to the Studio.
3. **"Never ingested" for test results.** Keep MD-7: no run result becomes a delivery fact. Concept
   00 and 07 go further, though, and say test results are "never ingested", which also rules out
   showing them. The adopter's run records, its acceptance check, and feedback 02's acceptance task
   ("whether a paused-rebuild example has native-backend evidence") argue for a labelled join in a
   view (rec 7). The concept text is the place to change.
4. **A hand-kept decision registry instead of a generated index.** v0 generated its index of
   decision records, and gen 1 generated `DECISIONS` pages from the same graph (annotation scout §2).
   The Protocol keeps `DECISIONS.md` by hand and makes it the ratification evidence for decision
   readiness. If a decision Spec's own `ready`, plus an authored ratified name, became the evidence,
   the index would become a projection and one hand-kept store would go (rec 4).

Not worth re-opening on this evidence: seven readiness rungs (the adopter itself declined a
`designed` rung, feedback 03); MCP for agents (agents script the graph and no app caller exists);
a forbidden-dependency validator (the adopter's own gate works under MD-38); and test results as
graph facts.
