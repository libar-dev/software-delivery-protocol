## Top recommendations

1. **Reopen architecture before code.** Supersede the narrow part of `spec:decisions.architectural-annotation` that makes a component exist only at a realizing anchor. Start `spec:model.planned-architecture` at scoped. Preserve the distinction between intended architecture and anchored realization; do not manufacture CodeNodes to make a design visible.

2. **Separate design comparison from exhaustive code impact.** The graph comparison promise already lives in `spec:consumers.impact-graph`, idea, but its blocking question concerns language-neutral symbol extraction. A scoped `spec:consumers.design-diff` can compare Specs, entries, questions, relations, and bindings across commits without solving that problem.

3. **Define interface requirements and provider selection.** Start `spec:model.architectural-contracts` and `spec:model.runtime-composition`, model/scoped. Establish what `uses` cannot say before selecting new node or edge names. Contract-kind Specs may supply the intended interface identity.

4. **Prove composition with a small manual-factory example.** Show a planned contract, two providers, one selected composition, a missing requirement, and a test substitution. This tests general semantics without committing the Protocol to Effect or Awilix.

5. **Give external boundaries and event flow a design-time home.** Start `spec:model.external-boundaries` and `spec:model.event-topology`, model/scoped. These matter to reviewing designs ahead of code and are not adequately represented by generic dependencies alone.

6. **Define fact attribution independently of `claim`.** Start `spec:extraction.fact-attribution`, contract/scoped. Preserve source location, extraction method, and external evidence identity where needed. Keep `declared`/`anchored`/`inferred` as epistemic categories.

7. **Turn Studio questions into owned model contracts.** Runtime composition, schema bindings, and execution evidence currently have UI questions but no supplying contracts. The Studio should consume those contracts rather than determine them incidentally.

8. **Add test evidence without changing `has-verifier`.** Start `spec:observation.test-evidence`, contract/scoped. A binding, a particular execution, its commit, and its result answer different questions. The adopter’s pinned-declaration comparisons provide a concrete consumer.

9. **Use existing readiness machinery before expanding it.** Prospective floor failures, keyed questions, and typed dependencies already support iterative design. Configurable floors are captured; they should follow a demonstrated need, not a return to v0’s seven-rung ladder.

10. **Defer interoperability formats and cache machinery.** JSON-LD, SHACL, generated ID unions, and hash-based rename suggestions are legitimate uncaptured claims, but they have less immediate design value than planned architecture, comparison, and composition.

## Departures worth re-opening

**The realized-only Component rule is the strongest case.** The ready [architectural-annotation decision](/Users/darkomijic/dev-libar/software-delivery-protocol/specs/decisions/architectural-annotation.sdp.md) explicitly says an unrealized component lives in Specs and has no CodeNode until an anchor exists. That prevents fake realization, but leaves the intended architecture without an equivalent structural view. The scoped Studio architecture and runtime questions expose the consequence directly. Reopen the representation of planned architecture while preserving anchored realization as separate evidence.

**The refusal of additional structural semantics deserves a narrower review.** The [structural-anchor decision](/Users/darkomijic/dev-libar/software-delivery-protocol/specs/decisions/structural-anchor-semantics.sdp.md), retained in the architectural-annotation ruling, rightly refuses `implements` as a duplicate of code-to-Spec `satisfies`. But v0 also asks a different question: which implementation provides an interface, and which composition selects it? Restoring that distinction need not restore the ambiguous `implements` slot. A superseding decision should state the distinct semantics and endpoint contracts.

**The projection freeze should reopen only for a concrete reader need.** The [shipped-projections decision](/Users/darkomijic/dev-libar/software-delivery-protocol/specs/decisions/shipped-projections-frozen.sdp.md) requires a superseding decision for reshaping the existing views. The adopter’s [feedback on iterative review](/Users/darkomijic/dev-libar/libar-platform/docs/feedback/sdp-feedback-02.md:118) supplies specific evidence: compare changes since a design pass, inspect declaration differences, and keep rationale near the affected design. A new comparison view may satisfy that need without reopening every shipped projection.

**Core enforcement of architecture constraints is a conditional case, not an immediate recommendation.** The architectural-annotation decision leaves negative dependency checks to adopter gates and accepts multi-node `uses` cycles. V0’s runtime checks concern different facts, such as an unresolved provider or incompatible lifetime. First model those facts and prove an adapter check. Only then decide whether any conformance check belongs in the Protocol.

I would retain the departures that preserve one Spec primitive, truth-free Packs, independent design readiness and delivery facts, explicit verification bindings, and ordinary source edits. None blocks the design-management improvements above.
