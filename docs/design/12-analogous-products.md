# 12 — Analogous products

This document condenses a survey of products that work on problems next to the Protocol's, from
developer portals and architecture as code to requirements tools, living documentation and AI
spec-driven development, into what each one teaches the design of the Protocol's readings. It is
design material, not intended truth: where it touches what a projection does, the carrying Specs
win on conflict.

**About the product facts.** They were gathered from public pages (vendor documentation, blogs,
community threads and a few third-party reviews) and may change. Products in this space are renamed,
acquired, repositioned or shut down often, and several below already have been. Each category ends
with its sources; check a product again before relying on a detail.

**About the Protocol claims.** Every statement about what the Protocol does was checked against the
graph; the queries are listed in [the last section](#how-the-protocol-claims-were-checked). The
design words the [README](README.md#words-used-here) marks provisional (reading, persona, role home,
object page, basis line) keep that status here. Every lesson is a candidate for the design pass,
not a commitment.

## How to read the tables

Each product gets one row:

- **Where truth lives:** the product's source of truth and how its views are derived from it.
- **Role-specific views:** who gets which view, and whether the views are designed or configured.
- **Lesson:** one idea worth carrying over, put into Protocol terms. Anti-patterns are folded into
  the lessons and into the [cross-cutting lessons](#cross-cutting-lessons).

## Developer portals and architecture as code

| Product | Where truth lives | Role-specific views | Lesson for the Protocol |
|---|---|---|---|
| **Backstage** (software catalog, TechDocs, catalog graph) | Hand-written YAML descriptors in each repository, ingested into a database. Relations are derived by processors, never authored. TechDocs is Markdown built to static HTML in CI. The served catalog lags the repository and names no commit. | By entity kind, not by role: each kind gets a page assembled in code from plugin cards. Leader views come only from plugins. | Put a Spec's own findings and absences in a fixed, unconditional region of every reading of it. Backstage has an orphan banner and a processing-error panel, but they appear only where someone wired them in. |
| **Tech Insights and Soundcheck** (scorecards for Backstage) | Time-stamped facts collected on a schedule, beside checks declared in configuration that judge those facts. | Owners get a scorecard tab. Leaders get a group picker, summary tiles, a compliance table and drill-down to teams "needing attention". | Borrow the drill-down (scope picker, tiles, table, pre-filtered list) without the compliance percentage. Navigate the graph's own hierarchy (roadmap entry, Pack, Spec), show counts of named kinds, and make each count open the list behind it. |
| **Port** | The vendor's database. Its schema can be edited in the UI, through infrastructure as code, or by asking an assistant in natural language. Derived values are typed as derived (mirror, aggregation, calculation). | A personal home ("my entities"), private and shared pages, and a column per scorecard rule in every catalog table. | Give every table of Specs automatic columns for delivery facts and findings, mark each cell with its claim or its outside input, and never total the columns into a percentage. |
| **Cortex** | YAML descriptors, edited in the UI or owned by Git, chosen per entity type. In one documented mode the UI silently overrides Git. A query language evaluates scorecard rules. | A "my work" homepage of failing rules with due dates, catalogs per type, leader metrics, and an MCP server for assistants. | Every finding and every absent cell should carry what produced it: the edge, entry address, source line and recipe. Cortex puts the failing value inside the rule's message, so the reason sits in the finding. |
| **OpsLevel** | A SaaS catalog with optional repository YAML. Checks form a rubric of categories by levels, and a service's level is computed. | A Maturity Report answers the service owner's "why this level, and what comes next". Leaders get roll-ups; campaigns push standards. | Base the readiness author's "what stands before the stated next rung" reading on this layout: the four rungs as columns, the stated rung beside the floor reached, and under each rung the unmet floor clauses with their locations. Replace OpsLevel's "Fix This" with composing scoped intent, so the view stays read-only. |
| **Structurizr** | A plain-text DSL workspace in the repository: one model, many views, documentation and decision records. CI validates and exports it. | By C4 level: system context for non-technical readers, containers and components for engineers, deployment for operations. Filtered views by tag, and question-driven overlays it calls perspectives. Its own docs say the as-code approach shuts out people who do not write code. | Build role readings as selections over a few shared readings (Pack, Spec, architecture, roadmap), so a Spec reads the same in every role and only selection and emphasis change. A lighter export must say what it left out: Structurizr's static site drops documentation and decisions without saying so. |
| **LikeC4** | A typed DSL in the repository. Views are predicates over the model. An MCP tool returns an element together with the views it appears in. | Views scoped to an element with click-through drill-down, a landing page curated by tags, and embeddable views. | Keep each role reading's selection as reviewable text, the way a perspective (recipe 37) is corpus data. Show on each Spec which readings include it, so a Spec no reading selects becomes a visible absence. |
| **IcePanel** | A shared model in the vendor's service; drafts fork it for future-state design. Links from model objects to repositories were polled, then withdrawn as too fragile. | C4 zoom levels, tag groups that highlight, pin, focus or hide objects, step-through flows, and share links. | Put a count of findings and absences in the header of every reading, scoped to what that reading shows (IcePanel's inaccuracy count is "contextual to what you're looking at"). Count named kinds, not one score, and link the count to the list. |
| **arc42 and docToolchain** | Prose chapters and diagrams as code in the repository, reviewed in pull requests and published by CI. Drift is caught by review habits, not derivation. | A field-tested table mapping stakeholders to the sections they need (arc42 FAQ B-15): managers, product owners, developers, operators, testers, neighbouring teams, and lately an LLM agent. | Seed the role-by-reading matrix from that table, translated into graph material (a tester to verifier bindings, example-space coverage and rule coverage; management to roadmap entries, decisions and constraints). Then refine it the arc42 way: show each role a cheap generated reading of a real Pack and revise from feedback. |

## Requirements, ALM and living documentation

Jira and Linear are included as a contrast: they hold process state, not delivery intent.

| Product | Where truth lives | Role-specific views | Lesson for the Protocol |
|---|---|---|---|
| **IBM DOORS Next** | A server database of typed artifacts in modules, with typed links. Every reading happens inside a configuration: a working stream or a frozen baseline. Link validity is computed from the content at both ends of a link, and people then mark links valid or invalid. | No designed role homes: saved views, a link explorer, configuration compare reports and dashboards built by admins. | Derive "the other end of this relation changed since the base" from the design diff (recipe 35), with a worst-case summary on the Spec's page. Acknowledgement is an ordinary carrier edit that git records, never a "mark valid" button. The always-present configuration menu supports a basis line at the top of every reading. |
| **Jama Connect** | An item database plus an admin-defined model of the relationships expected between item types. Coverage and gaps are computed against that model. Reviews are versioned snapshots. | A trace view for engineers and QA; a trace explorer for leads and auditors in which each metric opens a filtered list; a review centre with moderator, reviewer and approver roles and e-signature. | Copy the drill from aggregate to filtered list, never the single trace score. Show "expected relation absent" per relation kind with its scope stated in the reading: the gap signal expects a verifier only on a Spec stated `ready`. Comparing review rounds maps onto reading a Pack at a proposal's base against head. |
| **Siemens Polarion** (LiveDocs) | Work items with full revision history. LiveDocs show them as Word-like documents in which every paragraph is an item; collections pin items at a revision for a release. | Authors and reviewers in LiveDocs, engineers in tracker tables, managers and QA in report pages that admins build, compliance through baselined collections. | The strongest reviewer reading is document-shaped over typed items: a Pack read top to bottom like a specification, each block a linked Spec carrying readiness, claim and delivery facts inline. The Protocol avoids Polarion's confusion over two homes for one item only while documents stay readings. |
| **PTC Codebeamer** | Tracker items joined by links that can mark a downstream item "suspect" when an upstream item changes. Reviews are snapshots. | A configurable traceability browser with presets that admins save, a review hub with moderators and reviewers, and suspect badges that open the upstream diff. | Encode a reading's selection in its link, so a reviewer can paste an exact reading into a pull request with no server; the Studio already routes one filter this way (the capability map's epic filter). Open a review against a proposal base with what moved since it (recipe 38). An impact indicator should open the actual content diff. |
| **SpecFlow+ LivingDoc** (end of life) | Gherkin feature files. A closed-source generator rendered an HTML report or an Azure DevOps tab, with or without test results. It reached end of life with no direct substitute. | One view with a switch: product owners read scenarios without results, testers read pass and fail. | Keep intent readings complete without run evidence, and treat CTRF run reports as an optional, named overlay on the same reading. Keep the self-contained Pack export open and stable: people who lost LivingDoc asked for exactly a single offline file. |
| **Cucumber reporting** | Feature files plus one canonical event stream from which every report format is derived. A hosted service shares a run's report by URL and deletes it after about a day unless an account keeps it. | Essentially none: one run-centred report for everyone, with plugins adding overviews. | Confirms "one model, many formatters", but the Protocol's centre is intent stamped at a commit, with run evidence a named input. Any "publish and share" in a commercial Studio must give durable, stamped links, never expiring ones. |
| **Serenity BDD** | Feature files or tests, arranged in a requirements hierarchy taken from folders or from `@Epic`, `@Feature` and `@Story` tags, merged with outcomes at each build. | A requirements-first report aimed at the whole team, including auditors, with the most important detail first. | Keep the requirements-first, layered reading, but split Serenity's single "pending" into separate absences: no verifier bound, verifier bound but no run evidence supplied, run evidence failing, example-space value unbound, readiness stated below `ready`. |
| **adr-tools** | Numbered Markdown decision records in the repository. Supersession is written into both files; a generated graph shows filing order and declared links. Status is edited by hand. | None: a list, a generated table of contents and a graph image. | A decision-trail reading should show what each decision shaped: follow `decidedBy` to the Specs and on to code annotated as architecturally significant (the architectural-annotation decision, MD-38), and show supersession both ways, as the decision register (recipe 31) already lists it. |
| **Log4brains** | Decision records in the repository, built into a static site by CI, with dates and authors taken from git and a live preview while writing. Planned links from code to decisions never shipped. | One site for everyone: a timeline by month, search, status badges and package labels. | Its unmet demand, code linked to decisions and a decision backlog, is material the graph already holds: anchors, decision Specs, and open questions with a `decider`. A read-only decision timeline could pair git dates with those relations. `sdp studio --watch` is the Protocol's live preview and can be presented to authors as such. |
| **Jira** (contrast) | A work-item database whose status moves through configured workflows guarded by conditions and validators; some transitions fire on repository events. Requirements live in descriptions and linked pages. | Strong role surfaces over one store (boards, backlogs, dashboards, saved queries, service queues), all configured by users or admins. | Stay a membrane: link to tickets, never mirror their states or show one as a delivery fact. Saved, shareable queries are a precedent for named, shareable readings backed by recipes. A binding is not a verdict, and a leader reading must say so. |
| **Linear** (contrast) | Issues, projects and initiatives in the vendor's database. Project health (on track, at risk, off track) is written by leads when reminded, with derived progress attached when it moved. | Engineers work in issues and cycles, leads write updates, leaders read rolled-up initiatives pushed to an inbox and chat. | Put authored narrative and derived facts side by side and visibly apart: the reasons the author writes around the roadmap memo (recipe 55) next to the need the graph derives for each entry. Never merge the two into a health colour. Leading with what changed since the reader's base is a good attention pattern for role homes. |

## AI spec-driven development and code intelligence

| Product | Where truth lives | Role-specific views | Lesson for the Protocol |
|---|---|---|---|
| **AWS Kiro** | A folder per feature in the repository with requirements, design and tasks files, each generated from the one before with an approval at every step; the agent writes task progress back into the tasks file. Steering files hold standing project memory. A review on martinfowler.com found the specs are not kept up after their task. | None by role: everyone reads the same three files. Review aids include comments on exact passages sent to the agent, and a requirements analysis that names the requirements involved and offers fixes. | Use Kiro's finding card for honesty findings and open questions: the Specs involved, a plain reason, and three ways out (change the intent, the code or the verifier), each becoming scoped intent. Kiro's "dismiss as intentional" lives in the UI; the Protocol's equivalent must be a visible, authored edit in the repository. |
| **GitHub Spec Kit** | A constitution file plus a numbered folder per feature (spec, plan, tasks, research, contracts, checklists). Teams choose whether finished specs freeze, stay living or flow back. Its analysis is read-only, and its converge step only appends tasks and never rewrites intent to match code. | None visual; roles are implied by commands. Checklists belong to the reviewer, and the implementing agent may not tick them. | Converge's contract matches the Protocol's drift rule. Give Pack readings the same two outcomes: no drift (an empty drift alarm, recipe 2, and no open honesty finding), or a list ordered by severity with the scoped intent each item needs. Avoid Spec Kit's file sprawl: show plan- and task-like views as readings over one Spec enriched in place. |
| **Tessl** | Began as spec-as-source (one spec per generated code file), then repositioned as a registry of agent context (rules and skills) scored by reviews and evals, with LLM-judged verifiers kept in the repository. | Administrative roles; organisation-wide context and findings views for platform leads. | "Candidate until committed": anything AI-drafted that a reading shows is labelled with its model and source commit until it travels through git and the checks, as the provisional answer in `spec:consumers.ai-assisted-reading` proposes. Every finding names the check that produced it, so a judgement is never mistaken for a deterministic fact. |
| **GitHub Copilot Workspace** (shut down) | A session started from an issue: an editable "current state / desired state" spec, a file-by-file plan and an editable diff. Nothing persisted in the repository; the pull request was the durable record. It was folded into the coding agent. | The developer drives; reviewers got a read-only link to the session from each pull request. | Lay out an engineer's or architect's Spec reading as desired (authored intent) against current (delivery facts, bindings, inferred structure), with the gap shown as named absences. Make the stamped pull-request preview the default way into review: because it is stamped, it cannot become the stale snapshot that Workspace's shared links became. |
| **Cursor** (rules, plan mode) | Code is the truth. Rules in the repository (plus team rules in the vendor dashboard) and agent-written plans are context. A rule applies always, by the agent's judgement, by file pattern or on mention. | Developers only; admins manage team rules. | Borrow the rule-application vocabulary for a reading's hand-off to an agent: what is always included (the Spec, its blocking questions, the stamp), what is included because of scope, and what was left out. The context bundle (recipe 36) already states its scope and what it left out. |
| **Claude Code** (instruction files, plan mode) | The repository: committed instruction files load by directory, while personal memory and plans stay outside it. Guidance is kept apart from enforcement (permissions and hooks). | None visual; `/context` shows exactly what the agent received. | Copy `/context` into every reading and hand-off: list which Specs and graph facts were included, at which commit. A curator reading could flag prose that quotes facts the graph derives (counts, readiness), which the handbook ([AGENTS.md](../../AGENTS.md)) already treats as drift. |
| **Sourcegraph** | Code across all repositories; Sourcegraph is an index derived from it. Navigation results are precise (from compiler indexes) or search-based. Batch changes reconcile code hosts to a declarative spec; insights turn search queries into time series. | The clearest role split surveyed: engineers (search, navigation), migration owners (batch changes with preview and burndown), leaders (insights dashboards), agents (context APIs). | Leaders accept progress derived from the repository rather than from tickets when two rules hold: the recipe behind every number is visible, and stated readiness, floor reached, realization and verifier coverage stay separate series, never one "% done". Show each edge's claim on its own row, as Sourcegraph keeps precise and search-based results apart. |
| **CodeSee** (now GitKraken Codemaps) | Code. Maps were generated from file dependencies; human notes and tours were stored in the vendor's service and disappeared with the product. | Developers got dependency maps, reviewers a map per pull request, newcomers tours, leaders an ownership legend that names files needing an owner. | Scope every diagram to a question: a reviewer's default diagram is the blast radius of a change or a Pack's boundary at a commit, with a complete text equivalent. Keep any human arrangement (a tour order, a saved selection) as data in the repository, as perspectives already are, so it outlives the tool that renders it. |
| **Swimm** | Prose written in Swimm's editor with typed references to code (snippets, names, paths) that sync automatically. A pull-request check marks affected documents "potentially out of date" and can block the merge. Its homepage now leads with modernisation services. | Developers read documents in the IDE beside the code they reference; newcomers get playlists; reviewers get the check. | Beside each binding, show whether its anchor still resolves at the stamped commit, and name an unresolving binding as its own absence (it confers no delivery fact, and referential integrity reports it). Offer people the reverse lookup from a source file to its Specs that `g.byFile` already gives agents. Never rewrite anything silently. |
| **Mintlify** | MDX in git, rendered as a site with previews. A background agent drafts documentation updates from code and connected tools and always opens a pull request. Agents read the same content as llms.txt, Markdown pages and MCP. | Readers get the site, AI tools get agent formats, documentation owners get a suggestions inbox with diff stats and preview links. | Give every Studio page an agent twin: a per-page "copy as scoped context" (Markdown, graph addresses, stamp) and a site index for agents, so a reading and an `sdp q` answer are visibly the same content. AI-drafted changes arrive only as change proposals against a named base. |
| **Docusaurus** | Markdown in a docs folder; tagging a version copies the folder. Banners mark unreleased and unmaintained versions, "edit this page" links to the source file, and last-update data comes from git. | None by role; the axes are version and locale. | Keep the version banner but derive it from the stamp: which commit the reading projects and where that commit stands (main, a preview against its base, an older stamp). An "open at source" link per entry could build on the location table and the stamp's source template, keeping the rule that a view never writes. |
| **OpenSpec** | Current specs in one folder. Each change is a folder with a proposal, a design, tasks and delta specs (added, modified, removed), merged into current truth when archived. | None by role; a reviewer reads the change folder. | Lead a readiness author's review with the delta (clauses added, changed and removed, readiness moves) against the base (recipes 35 and 38), with the whole Spec one disclosure away. No archive step is needed: the merged commit is the new truth. |

## Cross-cutting lessons

| Lesson | Seen in | What it asks of the readings |
|---|---|---|
| **Where truth lives predicts who is reached.** | Repository-first tools (Structurizr, LikeC4, arc42, adr-tools) keep one truth but lose people who do not write code. Interface-first tools (Port, Cortex, IcePanel, the ALM suites) reach everyone but end with split truth. Products that kept truth in a session or a vendor's store (Copilot Workspace, CodeSee, Tessl's first framework) were shut down or repositioned; repository artifacts and indexes derived from them lasted. | Repository-only truth with strong readings for people who never open the repository: the gap this design pass exists to fill. Borrow principles rather than features from this set, since the features keep changing. |
| **Explain the state; do not score it.** | OpsLevel's Maturity Report, Cortex's failing values in messages, Kiro's finding card, Spec Kit's analysis ("fix them at the source"). Single scores hide distinctions: Jama's trace score depends on filters the reader cannot see, Serenity's "pending" covers several absences, Soundcheck ranks teams by compliance percentage. | Show the ladder, the stated rung beside the floor reached, and the located unmet clauses; send each fix to the Spec that owns it. No progress score ([PRODUCT.md](../../PRODUCT.md)). |
| **Role readings are selections over shared readings.** | Structurizr's filtered views and overlays, IcePanel's highlight, pin, focus and hide, LikeC4's predicates. Elsewhere, role views are left to admins: saved views, presets, dashboards, saved queries. | Role homes over the same object pages, so a Spec reads the same for every role. Role readings that are designed, not configured, would be new in every category surveyed. |
| **Keep facts, judgements and certainty apart.** | Tech Insights (facts apart from checks), Port (derived values typed as derived), Sourcegraph (precise apart from search-based), Swimm (synced apart from "potentially out of date"), Tessl (linters apart from LLM verifiers), Kiro (property tests as "evidence ... not a proof"). | Claims, stated readiness, floor reached, delivery facts and findings stay visibly and structurally distinct, never merged into one cell; every finding names its check. |
| **Honesty signals belong where the reader is looking.** | IcePanel's inaccuracy count, scoped to the open diagram; Backstage's orphan and error banners, which vanish when nobody wires them in. | A reading-scoped count of findings and absences in every reading's header, unconditional. |
| **Readers must know which version they are reading.** | DOORS Next's configuration menu, Polarion's revisions, Docusaurus's banners. The reverse: Backstage's lagging catalog, scorecards polled on a schedule, Copilot Workspace's stale shared snapshots. | The basis line (corpus commit, engine, base, supplied inputs) at the top of every reading, as prominent as DOORS Next makes its configuration (a candidate: today a `file://` page and a Pack export show no stamp, so an always-present line needs a "not stamped" state or a change to `ready` rules; [08](08-what-the-repo-settles.md#4-view-state-and-commercial-surfaces)). |
| **Change impact is the most valued and most resented feature.** | DOORS Next moved from timestamps to content; Codebeamer's suspect badge opens the diff. Both make people clear suspects by hand, which turns into noise in large projects. | Derive "changed since the base" per relation from the design diff, open the content diff on click, and route acknowledgement through a carrier edit and git. |
| **Review works in rounds over a base, delta first.** | Jama's review versions, Codebeamer's "restart for changed items only", OpenSpec's deltas. Böckeler: an effective spec-driven tool needs "a very good spec review experience"; Spec Kit's many files per spec were "tedious to review". | A Studio review reading opened against a proposal base leads with what moved (recipe 38); Design Review itself stays frozen under the shipped-projections decision (MD-32). Readings are built for review: delta first, finding cards, scoped diagrams, the whole Spec behind disclosure. |
| **Reviewers want document order over item identity.** | Polarion's LiveDocs, DOORS Next modules, Serenity's layered narrative. | A Pack reads top to bottom like a specification while every block stays a linked Spec, and the document never becomes a second place to edit. |
| **Living documentation fails when it centres on test runs or is closed.** | LivingDoc's end of life, Cucumber's expiring report links, Serenity showing nothing before tests run. | Intent readings complete without run evidence; run evidence an optional, named overlay pinned to its commit; the Pack export open, stable and self-contained. |
| **Every human view needs an agent twin, and every hand-off states its scope.** | Mintlify's agent formats and per-page copy, Claude Code's `/context`, Cursor's rule-application modes, LikeC4's "which views include this element". | Each reading hands an agent the same scope (the context bundle's parameters), saying what was included, why, and what was left out, at which commit. |
| **AI-drafted changes travel as proposals.** | Mintlify's agent pull requests, Tessl's candidate verifiers ("isn't part of your repository's policy until you ... commit it"), Spec Kit's append-only converge, Copilot Workspace's pull request. | Confirms that a view never writes: AI output is a labelled candidate until it passes through a change proposal, git and the checks. |
| **Authored status is the common weakness.** | ADR status text, Jira transitions, Linear health, review approvals and suspect clearing in ALM tools, task checkboxes in Kiro, Spec Kit and OpenSpec. Sourcegraph shows leaders accept derived progress when the query behind it is visible. | Where an authored judgement is legitimate (the reason for a roadmap entry's place, a decision's rationale), show it as attributed narrative beside derived facts, never as a fact. |
| **Scope diagrams to a question.** | CodeSee's per-pull-request maps outlived its whole-repository maps; Copilot Workspace listed the files before showing the diff. | Default diagrams answer one question (a blast radius, a Pack's boundary) and carry a text equivalent; human arrangements live in the repository. |
| **Ceremony must scale with the problem.** | Kiro added a one-pass mode to skip its own approvals; Spec Kit recast its phases as independent entry points. | With no gates to pass, readings should scale from one Spec to a Pack to the roadmap without adding steps. |
| **Seed role design from field evidence, then iterate with samples.** | arc42's stakeholder table and its advice to show each stakeholder cheap examples and incorporate their feedback. | Fits a long design pass with cheap, regenerable readings better than an information architecture fixed up front ([09](09-design-method.md)). |
| **Regulated buyers expect audit packages.** | Word and Excel trace exports, signed review records, baselines named after release gates. | An auditor reading probably needs a printable, single-file evidence set keyed to a commit; the Pack export and print-as-document are the starting point. |

## What this means for a commercial Studio (exploratory)

The core is and stays open source and free. A commercial Studio is under consideration as a web
app, a desktop app and a CI/CD surface ([04, section 5](04-reading-model-and-ia.md#5-surfaces));
nothing here decides its scope. The survey suggests where such surfaces would earn their keep and
where they would break the Protocol's rules:

- **Where the analogues' paid value sits:** people and ownership, notifications, comments and
  review threads, saved and private readings, history and trends, views across an organisation.
  Each is product state, not delivery truth.
- **What to avoid:** Cortex's mode in which the interface silently overrides Git, Port's schema
  edits by chat, CodeSee's notes lost with the vendor, Cucumber's links that expire. In a commercial
  surface, delivery truth stays in the repository, shared links stay durable and stamped, and any
  human arrangement worth keeping can be exported to the repository.
- **What lasted:** repository artifacts and indexes derived from them. A commercial Studio that is
  one more projection of the same graph inherits that durability.

Two needs this survey found, "the other end of this relation changed since the base" and which

## Questions for the research backlog

These are design questions for many cycles of work with real readers, not owner decisions to
settle now. Each pairs a persona or role from [01](01-roles-and-perspectives.md) with a job.

1. Does an explanation-first "what stands before the stated next rung" reading help a readiness
   author or decider decide faster than today's Pack page?
2. Can a leader reading built from counts of named kinds, with drill-down and no percentage, earn a
   leader's trust? What do leaders do when no single number is offered?
3. Will an auditor accept stamped readings, a Pack export and git history in place of a signed
   review record, or does a commit-keyed evidence set need a reading of its own?
4. Does a derived "changed since the base" indicator give reviewers the value of suspect links without
   their noise?
5. Does a reading-scoped count of findings and absences in every header help, or does it become
   noise the way suspect links did?
6. Which personas need intent where they write code (the IDE, the vault) rather than in the Studio?
7. Which habits from the analogues (comments, notifications, private drafts) belong in a commercial
   surface, and can each stay product state without becoming delivery truth?

These questions are carried in [06](06-design-cycles.md#design-questions-for-the-long-horizon).
